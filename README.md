# LLM Analytics Agent

![Analytics agent](assets/agent_eye_loop.gif)

An AI agent that answers business questions in plain English by writing and running its own SQL, built to act like a BI analyst at a tech company like Intuit.

Across three rounds of evaluation, accuracy improved from **1/5 to 5/5** and SQL queries dropped from **23 to 9**. A final test with realistic manager questions showed where the agent still falls short: it can produce accurate numbers but a misleading conclusion.

**Skills:** Python · SQL · LangChain · AI Agents · Tool Calling · Prompt Engineering · LLM Evaluation

---

## How it works

![How the agent answers a question](assets/agent_flow.gif)

1. A manager asks a question, e.g. *"We cut the Paid Search budget in July 2025. What did that do to new customer acquisition?"*
2. The model decides which tool to call and writes the SQL.
3. The tool runs the query and sends back rows (or an error the model can fix).
4. The loop repeats until the model has enough data, then it writes the answer.

| Tool | What it does |
|---|---|
| `list_tables` | Shows each table's columns and example rows, so the agent learns the data format |
| `run_sql` | Runs a read-only SELECT query and returns up to 50 rows; errors come back as text so the agent can retry |
| `make_chart` | Turns a query result into a bar or line chart (PNG) |

**Stack:** LangChain (`create_agent`) · Groq (`gpt-oss-120b`) and Google Gemini · SQLite (in-memory, read-only) · pandas · matplotlib

## Data

> **The datasets are synthetic.** They were generated by `Claude Opus 5.5 model` for this project and are **not real Intuit data**. Product names are used only to make the scenario feel realistic.

Two tables, monthly, Jan 2023 – Dec 2025:

| Table | Rows | Contents |
|---|---|---|
| `intuit_revenue_data` | 864 | Product × acquisition channel: trials, new paying users, marketing spend, CAC, revenue, ROAS |
| `intuit_customer_segmentation` | 1,440 | Region × customer segment: active users, churn, ARPU, NPS, support tickets |

The data contains built-in business events (a Paid Search budget cut, a Small Business price increase, fast growth in India, etc.) so each evaluation question has a known correct answer. See [`DATA_README.md`](DATA_README.md) for the full list.

## Evaluation

I tested the agent with five questions per run, checked every answer against values calculated in pandas, and traced each mistake to its cause in the SQL.

### Run 1: vague questions, basic prompt (1/5)

![Run 1](assets/agent_eval_run1.gif)

| Q | Result | What went wrong |
|---|---|---|
| 1 | ⚠️ | Averaged a ratio column (`AVG(cac_usd)`) instead of dividing totals: $132.92 instead of $130.04 |
| 2 | ⚠️ | Right channel, wrong number: same `AVG()` mistake on ROAS |
| 3 | ❌ | Measured growth as users added, not percentage (the question didn't specify) |
| 4 | ❌ | Found the highest churn, not the biggest *increase* in churn |
| 5 | ✅ | Correct, but took 38.6 s guessing the date format |

### Run 2: clearer questions + example rows in `list_tables` (5/5)

![Run 2](assets/agent_eval_run2.gif)

| | Run 1 | Run 2 |
|---|---|---|
| Score | 1 / 5 | **5 / 5** |
| SQL calls | 23 | **9** |
| Empty queries | 4 | **0** |
| Total agent response time | 88 s | **33 s** |

Example rows fixed the date-format guessing, and clearer questions fixed the comparison logic.

### Run 3: realistic manager questions + full system prompt

Run 2 only worked because the questions spelled out the metric, period and comparison. Real managers don't ask like that, so in run 3 I moved that knowledge into the system prompt (data rules, analysis rules and an answer format) and asked questions the way an Intuit manager would: they know what was rolled out, but not its impact.

![Run 3, Q1](assets/agent_eval_run3_q1.gif)

On Q1 the agent scored **0.5/1**. Every number was correct, but the conclusion was misleading:

- **Wrong baseline:** it compared H2 2025 with H1 2025. H2 is always lower (−20% in 2024 with no cut), so it reported −52% instead of the fair year-over-year −36%.
- **Missed the big picture:** it never checked total acquisition, which actually **grew 3.7%** because other channels made up the gap.
- **Inefficient:** 7 queries and 92 seconds, one metric and one period at a time, where a single query would do.

---

## Key learnings

1. **The agent knows business terms, not how *this* company calculates them.** It knew what CAC means but averaged the precomputed `cac_usd` column instead of rebuilding it from totals (`SUM(spend) / SUM(new_users)`). It also had no way of knowing `revenue_usd` only covers newly acquired users. Company-specific definitions have to be supplied, ideally through a semantic layer of agreed metrics.
2. **Tools shape what the agent can see.** Adding 2 example rows to `list_tables` ended the date-format guessing (`'Dec'` vs. `'2023-12'`). Tool docstrings work as instructions: "Call this first" is why every trace starts with `list_tables`.
3. **Correct numbers can still lead to a wrong conclusion.** The hardest errors to catch were analytical, not mathematical: comparing against a seasonally lower period, and never checking the company-wide total.
4. **Efficiency has to be designed in.** The agent explores step by step and doesn't feel the cost of extra queries, so it ran 7 queries where one `GROUP BY` with `CASE WHEN` would do. Since every step resends the whole conversation, this drives up token use.
5. **Evaluation questions need to be precise too.** In run 1, one "wrong" answer came from an ambiguous question (absolute vs. % growth), not an agent mistake.

## Limitations

- **Small evaluation set:** five questions per run shows patterns, not reliability. Run 3 is complete for Q1 only.
- **Model change:** runs 1–2 used `gpt-oss-120b` (Groq) and run 3 used Gemini after free-tier limits ran out, so run 3 differs in both prompts and model.
- **Silent truncation:** `run_sql` caps results at 50 rows without telling the agent. The cap was hit twice (run 2, Q3 and Q4: 80 and 96 rows), but both final answers came from follow-up summary queries and matched the pandas-verified values.
- **Unused chart tool:** `make_chart` was built for a future interface; the agent never called it in the terminal-based evaluation.

## Next Steps
- **Metric definitions:** a short data dictionary (meaning plus formula per column) returned by `list_tables`, so definitions sit next to the data.
- **Metric tools:** e.g. `compare_periods(channel, metric, period_a, period_b)`, so the agent picks the analysis and tested code does the math.
- **Truncation warning:** return the true row count when results are cut off and tell the agent to aggregate in SQL.
- **Efficiency limits:** a step limit and a plan-first rule to reduce redundant queries.
- **Streamlit chat interface:** a front end for non-technical users, which would also give `make_chart` a purpose.

## Run it yourself

```bash
# 1. Create and activate a virtual environment
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # Mac/Linux

# 2. Install packages
pip install python-dotenv pandas matplotlib langchain langchain-groq langchain-google-genai

# 3. Add your API key(s) to a .env file (never commit it)
#    GROQ_API_KEY=...
#    GOOGLE_API_KEY=...

# 4. Generate the synthetic data
python generate_data.py

# 5. Run the agent and the evaluation
python agent_tool.py
```

### `intuit_revenue_data` — one row per month × product × acquisition channel

| Column | Type | Description |
|---|---|---|
| `month` | text | Month in `YYYY-MM` format (e.g. `2025-07`) |
| `year` | integer | Calendar year (2023–2025) |
| `quarter` | text | Calendar quarter (`Q1`–`Q4`) |
| `product` | text | QuickBooks, TurboTax, Credit Karma or Mailchimp |
| `acquisition_channel` | text | Organic Search, Paid Search, Paid Social, Referral, Accountant Partners or Email |
| `trials` | integer | Users who started a free trial |
| `new_paying_users` | integer | Trial users who converted to a paid plan |
| `conversion_rate` | decimal | `new_paying_users / trials` |
| `marketing_spend_usd` | decimal | Marketing spend attributed to the channel |
| `cac_usd` | decimal | Customer acquisition cost: `marketing_spend_usd / new_paying_users` |
| `revenue_usd` | decimal | Revenue from newly acquired paying users (not total company revenue) |
| `refunds_usd` | decimal | Refunds issued on that revenue |
| `net_revenue_usd` | decimal | `revenue_usd − refunds_usd` |
| `roas` | decimal | Return on ad spend: `revenue_usd / marketing_spend_usd` |

### `intuit_customer_segmentation` — one row per month × region × customer segment

| Column | Type | Description |
|---|---|---|
| `month` | text | Month in `YYYY-MM` format |
| `year` | integer | Calendar year (2023–2025) |
| `quarter` | text | Calendar quarter (`Q1`–`Q4`) |
| `region` | text | US West, US South, US Northeast, US Midwest, Canada, UK, Australia or India |
| `country` | text | `USA` for US regions, otherwise the region name |
| `segment` | text | Consumer, Self-Employed, Small Business, Mid-Market or Accountants |
| `active_users` | integer | Customers active that month |
| `new_users` | integer | Customers who joined that month |
| `churned_users` | integer | Customers who cancelled that month |
| `churn_rate` | decimal | `churned_users / active_users` |
| `arpu_usd` | decimal | Average revenue per user for the month |
| `revenue_usd` | decimal | `active_users × arpu_usd` |
| `nps` | decimal | Net Promoter Score (customer satisfaction, −100 to 100) |
| `support_tickets` | integer | Support tickets opened that month |
| `avg_tenure_months` | decimal | Average customer tenure in months |

**Shared keys:** `month`, `year` and `quarter` appear in both tables, so the agent can join or compare them by period.

> **Note on ratio columns** (`conversion_rate`, `cac_usd`, `roas`, `churn_rate`, `arpu_usd`): these are calculated per row. To get a rate across several months or groups, rebuild it from the totals (e.g. `SUM(marketing_spend_usd) / SUM(new_paying_users)`) instead of averaging the column. Averaging was the agent's main mistake in run 1.
